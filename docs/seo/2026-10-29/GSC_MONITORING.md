# Проверка результатов в Google Search Console

Изменения подготовлены локально 29 октября 2026. Дата публикации ещё не определена. Отсчёт эффекта ведётся от выпуска и переобхода, не от даты аудита. Техническая проверка кода не подтверждает индексацию в Google.

## До выпуска

1. Сохранить исходные показатели и дату выпуска. Свежий baseline находится в `GSC_BASELINE.json`: фактические даты 3–26 октября, 153 клика / 2 094 показа по дням. Отдельный отчет страниц — 157 / 2 375, запросов — 58 / 737. Не смешивать знаменатели.
2. Получить совместные строки **дата + запрос + страница**, по возможности за последние 8–12 недель. Если сайт имеет более короткую историю, сохранить доступные даты и не трактовать отсутствующие строки как нули. Сегментировать по стране и устройству; язык определять по префиксу URL, а язык самого запроса проверять отдельно. Брендовые запросы отделить от небрендовых.
3. Сохранить URL Inspection для приоритетных HY/RU страниц: цены, общий ремонт квартиры, новостройка, капитальный, косметический, под ключ, смета, общий дизайн и дизайн квартиры. Добавить контрольные EN/DE/FR страницы. Записать Google-selected canonical, user-declared canonical, индексируемость, дату последнего обхода и причины исключения.
4. До любых будущих объединений получить отчет внешних ссылок на **оба** URL, включая ссылки на старые aliases. Отсутствие этих данных блокирует вывод о безопасном слиянии, но не текущие добавочные улучшения.

## Как получить query + page

В интерфейсе GSC: «Эффективность → Результаты поиска», задать одинаковые даты, тип поиска, страну и устройство. Добавить фильтр по **точному запросу**, затем экспортировать вкладку «Страницы». Имя/сопроводительные данные экспорта должны сохранять запрос и все фильтры. Повторить для приоритетных запросов и сопоставимых недель. Выгрузка отдельных вкладок «Запросы» и «Страницы» без такого фильтра не дает связи между ними.

При наличии авторизованного Search Console API использовать `searchAnalytics.query`. Пример запроса для истории перед текущим аудитом, без предположения, что данные за весь период существуют:

```json
{
  "startDate": "2026-08-01",
  "endDate": "2026-10-26",
  "type": "web",
  "dataState": "final",
  "dimensions": ["date", "query", "page"],
  "rowLimit": 25000,
  "startRow": 0
}
```

Пагинация: увеличивать `startRow` на 25000, пока не получена неполная/пустая страница. Для проверки конкретного рынка добавить одинаковые country/device-фильтры в сравниваемых периодах; не объединять сегменты с разными фильтрами. Даже при пагинации API возвращает не гарантированно все строки; сохранять ограничения анонимизированных и невыданных запросов. Использовать отдельные контрольные итоги по датам и страницам. [Документация Search Analytics API](https://developers.google.com/webmaster-tools/v1/searchanalytics/query).

Наличие запроса в списке не означает, что для него уже есть строка в исходном отчете. Полная карта по пяти языкам — `AUDIT_AND_PLAN.md`, точные строки выгрузки — `GSC_BASELINE.json`.

Для каждой пары query + page считать клики, показы, CTR из сумм; позицию по периодам взвешивать показами, а не усреднять средние позиции без веса. Разбивать по неделям и сравнивать одни запросы в одинаковом сегменте. Доля показов URL среди URL одного запроса — диагностическая метрика распределения по страницам, не число уникальных поисков.

Сигнал проблемы: менее релевантная страница регулярно заменяет целевую по одной группе запросов, одновременно ухудшаются клики/позиции группы и отсутствует самостоятельное назначение содержания. Одновременные показы двух URL сами по себе не доказывают вред. Проверить выдачу, сезонность, спрос, изменения конкурентов, бренд, страну, устройство и другие релизы прежде, чем делать вывод.

## После выпуска

| Когда | Проверка | Действие |
| --- | --- | --- |
| День выпуска | 120 URL, sitemap, robots, пять языков, CTA, отсутствие новых redirect/noindex | Повторить HTTP-обход по production и записать версию релиза. Не менять одновременно URL и основную семантику |
| Через 3–7 дней | URL Inspection, выбранные canonical, доступность изменённых страниц | При необходимости запросить переобход нескольких приоритетных URL. Не отправлять массовые заявки на индексацию |
| Через 14 дней | Начало переобхода, исключения, query + page по кластерам | Исправлять технические регрессии сразу. По небольшим колебаниям позиций страницы не удалять |
| Через 28 полных дней после переобхода | Сопоставимые 28 дней: клики, показы, CTR, позиции одинаковых запросов; заявки отдельно | Оценивать весь кластер и целевой URL. Снижение вспомогательной страницы при росте целевой и группы не считать автоматически потерей |
| Через 6–8 недель | Устойчивость распределения запросов и квалифицированные заявки | Решить, нужно ли дальнейшее уточнение контента. Объединения — только отдельным согласованным планом с данными ссылок |

Главные критерии: сохранение органических кликов и полезных заявок по кластеру, сохранение индексируемых языковых страниц, более устойчивый выбор правильной посадочной. Рост позиции без сохранения релевантного трафика и заявок не является достаточным результатом.

Немедленный повод для отката конкретной правки: ошибочный canonical, noindex, 404/5xx, сломанная форма или язык. При падении трафика сначала проверить переобход, одинаковые условия сравнения и соседние релизы; возвращать только затронутый контент/ссылки, не откатывать прежние полезные улучшения всего проекта.

## Отдельно: редиректы на хостинге

`LIVE_REDIRECTS.json` фиксирует до трёх последовательных 308 для `http://shinex.am/`: HTTPS → www → `/hy`. На canonical HTTPS/www старый URL со slash и параметром переходит сразу на конечную страницу, параметр сохраняется. В приложении нормализация уже объединена; первые переходы задаёт хостинг. Изменение доменной конфигурации в этой работе не выполнялось. Можно отдельно спланировать сокращение цепочки с сохранением конечных URL и предварительной проверкой всех доменных вариантов.
