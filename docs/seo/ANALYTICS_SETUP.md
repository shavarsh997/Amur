# Конверсии и атрибуция

Используется существующий GA4 (`NEXT_PUBLIC_GA_MEASUREMENT_ID`). Дополнительный GTM-контейнер не устанавливается: два параллельных тега могут дублировать события. Если владелец переводит управление в GTM, сначала отключить прямую установку и воспроизвести один источник каждого события.

## Обязательная настройка перед выпуском

1. В GA4 Data stream → Enhanced measurement отключить автоматические **Form interactions** и **Page changes based on browser history events**. Код сам отправляет `form_start`, `form_submit`, `page_view`; `send_page_view:false` уже отключает начальный автоматический просмотр. Внешние настройки аккаунта не изменялись. Без этой настройки GA4 может добавлять собственные дубли, независимо от защиты React-кода. [Документация Google](https://developers.google.com/analytics/devguides/collection/ga4/views).
2. Не включать автоматический сбор пользовательских данных из форм. Не добавлять GA/GTM-переменные с именами, телефонами, комментариями, необработанными URL и referrer.
3. Зарегистрировать event-scoped custom dimensions: `form`, `calculation_type`, `cta_id`, `error_type`, `entry_source`, `entry_medium`, `landing_page`. `page_path` доступен также как параметр.
4. Пометить только `generate_lead` как основное ключевое событие заявки. Телефон и WhatsApp — отдельные микроконверсии, не подтверждённые лиды. `form_submit` и `calculator_complete` не считать заявками.
5. В DebugView проверить один просмотр при открытии/клиентском переходе, один form_start после первого изменения, одну попытку/ошибку/доставку на соответствующее действие. Проверить обновление страницы, Back, повторное открытие окна и ошибки отправки. Убедиться, что поля клиента и параметры URL отсутствуют в событиях. Настройку сбора и политику конфиденциальности подтвердить владельцу перед релизом.

## Контракт событий

| Событие | Когда | Что означает |
| --- | --- | --- |
| page_view | первый просмотр пути и смена пути | один ручной просмотр; повторный эффект не повторяет событие |
| cta_click | открытие контактов/формы или ссылка на Contacts | `cta_id`: contact_methods / message_form / contact_page |
| phone_click / whatsapp_click / email_click | нажатие соответствующей ссылки | один общий обработчик для всех ссылок, включая footer и mobile bar |
| form_start | первое изменение поля формы | `form`: lead / calculator; фокус и ререндеры не считаются |
| form_submit | фактический запуск действия отправки | попытка, в том числе неверные поля |
| form_error | ошибка валидации либо доставки | только классификация validation / delivery, без текста ошибки |
| generate_lead | Telegram API вернул успешную доставку | только `delivered:true` от Server Action; honeypot не считается |
| calculator_start | первое взаимодействие | один раз за открытие компонента |
| calculator_complete | корректные параметры переданы в контактную форму | расчёт ещё не доставлен; conversion только после generate_lead |

`generate_lead` означает приём Telegram API, не прочтение менеджером, квалификацию или продажу. Сбой сети после приёма может дать неизвестный результат; для строгой межзапросной идемпотентности нужен постоянный lead store/CRM, которого в проекте нет. Повторные React-эффекты не отправляют конверсии: события доставки вызываются один раз в результате конкретного action.

## Источники и конфиденциальность

`lead-attribution.ts` сохраняет первую публичную страницу и категорию источника в sessionStorage с 30-минутным сроком неактивности. Внутренние переходы не заменяют посадочную. Поддержаны известные поисковики, социальные источники и ограниченные utm_source/utm_medium. Неизвестные значения сводятся к campaign/external. Наличие gclid определяет google/cpc, само значение не сохраняется. Полные referrer, query, hash, utm_campaign, имена и контакты не сохраняются в атрибуции.

События содержат `entry_source`, `entry_medium`, `landing_page`; сервер повторно проверяет эти значения и добавляет их к заявке вместе с местом отправки. Страница должна входить в allowlist, сверяемый тестом с sitemap. Произвольные аналитические параметры отбрасываются. Блокировка GA или sessionStorage не препятствует отправке формы.

Чтобы не передавать возможные персональные сведения из query/referrer, `page_location` очищен, `page_referrer` пустой. Поэтому **не сравнивать стандартный GA session source/medium с прежней реализацией как непрерывный ряд**. Для текущего baseline использовать собственные `entry_source`/`entry_medium`: сессионный сегмент с `entry_medium=organic` и журнал доставленных заявок. Это ограниченная классификация источника, а не замена полной рекламной атрибуции. При отсутствии referrer/разрешённой метки источник может стать direct.

## Воспроизводимые проверки

`npm run analytics:check` проверяет allowlist, удаление лишних полей, источники, внутреннюю навигацию и отказ хранилища/GA. `npm run leads:check` использует реальный Server Action с подменой Telegram на сетевой границе.

Для browser test сначала собрать проект и запустить **отдельный** сервер:

```sh
SHINEX_BROWSER_TEST=1 TELEGRAM_BOT_TOKEN=test-no-network TELEGRAM_CHAT_ID=test-no-network node --import ./scripts/lib/mock-telegram.mjs node_modules/next/dist/bin/next start -H 127.0.0.1 -p 3102
node scripts/seo-browser-check.mjs http://127.0.0.1:3102
```

Playwright берётся из установленной dev-среды либо bundled runtime через `NODE_PATH`; `PLAYWRIGHT_EXECUTABLE_PATH` может указывать на существующий Chromium. Тест откажется отправлять форму, если сервер не отдаёт специальный mock-probe. Запросы GA заблокированы, события перехватываются в памяти. Результаты — `BROWSER_CHECKS.json`. Preloader нельзя использовать в production.
